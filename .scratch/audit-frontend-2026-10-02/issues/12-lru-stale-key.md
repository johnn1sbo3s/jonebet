## Agent Brief

**Category:** bug
**Summary:** O cache LRU deve gravar cada resposta sob a key da requisição, não sob a key vigente no momento da resposta.

**Current behavior:** A gravação no cache lê a key no retorno da request. Se a key mudou durante o voo (troca de página/modelo/data), os dados de A ficam cacheados sob a chave de B. Navegação futura a B é servida do cache sem nova requisição — exibindo bets/gráfico de outro contexto. O próprio comportamento de "pular refetch quando o cache tem valor" amplifica o dano.

**Desired behavior:** Cada resposta é gravada sob a key com a qual a requisição foi disparada, independentemente de a key vigente ter mudado. O cache nunca serve dados de uma key para outra. O refetch continua sendo pulado apenas quando o cache da key vigente tem valor legítimo.

**Key interfaces:**
- A camada de cache do composable de API de modelos: a key deve ser capturada no momento da request e usada tanto na leitura quanto na gravação (`onResponse` grava com a key da request, não com a reativa vigente)
- `getCachedData`: só pula o refetch se o valor cacheado pertencer à key sendo consultada

**Acceptance criteria:**
- [ ] Request disparada com key A, retornando com key já em B, grava os dados sob A
- [ ] Navegar para B não é servido com os dados de A do cache — dispara busca própria
- [ ] Navegar para A mostra os dados corretos, servidos do cache
- [ ] O refetch continua sendo pulado quando a key vigente tem cache válido
- [ ] Existe cobertura de teste para resposta fora de ordem entre duas keys

**Out of scope:**
- Mudar o tamanho, a estrutura ou a política de expiração do LRU
- Invalidação de cache por data
- Alterar o formato das respostas da API
